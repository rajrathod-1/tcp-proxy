A TCP proxy, routing around trouble.

A multithreaded Layer 4 proxy with an epoll event loop per worker, three balancing strategies, passive health checks that retry a refused connect on another backend, and a line of JSON telemetry for every connection. A browser has no sockets, so the proxy's balancer is compiled to WebAssembly below and given simulated backends to route to. The results further down are the real proxy under load on Linux.

    The real proxy, on Linux

    Under load

    Measured with the repository's own load generator and echo backend, all on loopback in a Linux 6.12 VM on an Apple M4 Pro, with backends, proxy and load generator pinned to separate CPUs. Each number is the median of three five-second runs; scripts/bench.sh reproduces all of them.

    Where the time goes

    One worker relays about 250,000 small requests a second and spends 3.9 µs of CPU on each: 0.4 µs in the proxy's own code and 3.5 µs in the kernel. Every request costs exactly four system calls, a read and a send in each direction, and each epoll_wait returns about 255 ready sockets, so the event loop's own cost is amortised away. What is left is the TCP stack, so the ways up are more cores, or fewer system calls per byte.

    The proxy adds about 28 µs to a round trip: two more hops through loopback. Scaling across workers is uneven here, and this setup could not separate kernel contention from the VM sharing eight performance cores between the load generator, the backends and the proxy.

    Eight connections streaming 64 KiB writes through three workers, with system calls counted from the proxy's own telemetry. Quadrupling the buffer from 4 to 16 KiB cuts the calls by four and multiplies throughput by five; past that, copying dominates and each step buys less. 16 KiB is the default because the buffer is paid for twice on every open connection.

    Three backends, one answering 20 ms late, and a new connection for every request, 48 at a time. Round robin hands the slow backend a third of the requests, so every client spends most of its time waiting on it. Least connections sees its open connections pile up and sends almost everything elsewhere: 15 times the throughput.

    A backend dies

    RetriesEjectionFailed requestsFailed connectsRequests / s

    One of three backends is killed 3 s into a 10 s run. Without retries, every connection sent to it fails. With retries, a refused connect is tried on another backend before the client has lost anything, but the dead one is still tried first a third of the time. Ejection takes it out after its first failure and lets one connect probe it every five seconds. The failures left are the requests that were mid-flight on the backend when it died: their bytes were already sent, so a Layer 4 proxy cannot replay them. Opening a fresh connection for every request, the proxy sustained 103,494 a second with a p99 of 0.92 ms.
